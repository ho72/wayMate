# 실제 내비 좌표·경유지 추가 및 제거 검증

> 최신 목표(v0.8)는 **탑승 전 모바일 추천·매칭 → Pleos 이동 경험**이며 [04 개발 명세](04_개발_및_연동_명세서.md)의 schemaVersion 4를 따른다. 이 문서의 당시 실행/검증 기록·v2/v3 계약은 보존한다. 이전 P06/P07 차량 매칭 방향을 새 목표로 적용하거나 이 기록을 모바일 매칭 완료 증빙으로 사용하지 않는다.

2026-11-11 · v0.1 · 실제 NaviHelper / Pleos 에뮬레이터 시험

## 1. 확인 결과

**실제 SDK의 M 추가 → 원래 D 유지 → M만 제거 → D 유지가 통과했다.** 앱 재시작 사이에 SDK 추가 호출이 반복되지 않는 것도 확인했다. 모의 결과나 수동으로 바꾼 앱 상태를 성공 근거로 사용하지 않았다.

| 단계 | 실제 관측 |
|---|---|
| D 설정 | requestRoute에서 예제 POI ID를 제외하고 좌표로 요청. 조회 D=(37.48544722,127.03636666), 경유지 없음 |
| M 위치 확인 | requestTrip으로 M의 POI를 독립 조회. ID=36khp2hdj2cfcm5nqhe3, 경로 진입점=(37.4127749,127.0947566) |
| M 추가 | addWaypoint(FIRST) 한 번. 현재 경유지 1개·M ID 일치·원래 D 유지. 두 SDK 관측으로 applied 확인 |
| 앱 재시작 | 소유 M·D 기록 유지, 새로운 물리 SDK dispatch 0건. 새 세션에서 POI 위치를 다시 확인 |
| M 제거 | removeWaypoint(FIRST) 한 번. 경유지 0개·원래 D 유지. 두 SDK 관측으로 removed 확인 |
| 종료 상태 | pending 없음, ownsM=false. 시험 D는 검토할 수 있도록 순정 안내에 유지 |

환경은 Pleos_Connect_2_1_API_34·사용자 10·NaviHelper 3.0.5·Navi Service 3.0.4·순정 내비 3.3.2-rc5-hotfix.3이다. APK 설치본과 로컬 빌드의 SHA-256 일치도 확인했다.

실제 SDK 증거·원문 좌표·관측 간격·이전 unknown 이력·APK SHA는 [검증 JSON](evidence/navi-waypoint-roundtrip-2026-11-11.json)에 있다. [M 추가 화면](evidence/navi-added-2026-11-11.png)과 [M 제거 후 D 안내 화면](evidence/navi-removed-2026-11-11.png)을 함께 확인한다. 원본 journal은 로컬 `mock-app/runtime/navi-final-removed.json`과 앱 전용 `files/navi-probe.json`에 보존했다.

## 2. 좌표 불일치 원인과 수정

### D: 예제 POI ID와 좌표를 함께 사용한 문제

[공식 예제](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/waypoint-settings)는 D 좌표 (37.48544722,127.03636666)와 POI ID 36khp37hh8gqcm5nqhe5를 함께 제공한다. 첫 시험에서는 요청 이름이 42dot이었지만 실제 조회는 (37.41289678,127.09383464)였다. 순정 화면도 가까운 42dot으로 안내했다.

**같은 좌표·이름·주소에서 poiId만 빈 문자열로 바꾸자 요청한 좌표가 그대로 반영됐다.** 따라서 그 예제 ID를 좌표와 무조건 함께 보내지 않도록 수정했다. 내부 검색 엔진의 구현을 추정해 보정하지 않으며, 현재 데이터에서 확인하지 않은 POI ID를 복사하지 않는다. 좌표 인자는 named argument로 전달한다. [SDK 릴리즈 노트](https://document.pleos.ai/docs/pleos-only/release-note/sdk-release-note)의 생성자 좌표 순서 변경과 구분한다.

### M: 현재 조합의 경유지 좌표 조회 0,0

좌표만으로 M을 추가하면 순정 내비 실제 경로에는 M이 반영됐으나 getWaypointInfo의 좌표는 (0,0)이었다. 내비 로그의 실제 routePointSet에는 입력한 M 위치가 있었지만, 경유지 정보 projection에는 0,0이 있었다. 이름만 보고 성공 처리하지 않고 이 시도는 unknown으로 보존·복구했다.

최종 방식은 다음과 같다.

1. **별도 SDK POI 위치 조회:** requestTrip에서 M ID와 기준 좌표를 보내고, 결과의 DESTINATION ID·위치를 확인한다. 이 응답을 현재 경유지 목록으로 간주하지 않는다.
2. **사전 검증:** 결과 ID가 M ID와 같고, 현재 세션·10분 이내이며, 고정 시험 M의 기준점에서 30m 이내여야 한다. 이번 경로 진입점과 기준점 차이는 실측 5.848m였다. 30m는 이 시험 POI의 진입점 검증 범위이며 모든 실제 장소에 일괄 적용하는 기준이 아니다.
3. **명시 승인 후 추가:** 검증한 ID를 RequestWaypointInfo에 포함해 FIRST에 추가한다. 호출 직전에 D·빈 슬롯·제한·화면 활성 상태를 다시 읽는다.
4. **현재 경유지 대조:** getWaypointInfo의 실제 현재 목록이 M 1개여야 한다. 유효한 좌표는 기준점/검증한 진입점과 비교하며, 좌표가 0,0인 호환 경로는 이름·POI ID가 검증한 M과 같아야 한다. D도 유지돼야 한다.
5. **원문 유지:** 이 조합에서는 POI 방식에서도 경유지 좌표가 0,0으로 반환됐다. 원문을 요청 좌표로 채우지 않는다. `verificationBasis=current_waypoint_poi_id_and_independent_sdk_lookup`와 독립 조회 근거를 함께 저장한다. 실제 좌표가 존재하는데 기준점/검증한 진입점과 다르면 거절한다.

이는 조회 호환 처리다. 순정 내비의 0,0 반환 자체를 고친 것으로 표시하지 않는다. 빈 ID·다른 ID·다른 이름·만료한 조회·다른 세션·범위를 벗어난 위치·다른 목적지·여러 경유지는 통과하지 않는다.

## 3. 성공·소유권·재시작 조건

[순수 검증 정책](../mock-app/vehicle/app/src/main/java/com/waymate/app/platform/navigation/RouteProbePolicy.kt)과 [SDK 시험 Activity](../mock-app/vehicle/app/src/realDebug/java/com/waymate/app/platform/navigation/NaviProbeActivity.kt)를 분리했다.

- requestRoute/addWaypoint/removeWaypoint 반환과 타이머는 성공 근거가 아니다. 타임아웃은 unknown을 남긴다.
- 목적지·경유지·route-state 세 응답을 모아 snapshot을 만든다. 같은 세션·증가 querySeq·dispatch 이후의 두 snapshot에서 목표 상태가 일치해야 한다.
- 첫 조회 완료 뒤 다음 조회 시작까지 실제 1초 이상 기다린다. SDK 응답 자체가 약 1.2초 걸릴 때도 이 간격을 확보하도록 조회 주기를 보완했다.
- ROUTE_GUIDING·isRouting=false와 D/M 상태를 함께 확인한다. 현재 내비 조합에서 전달되지 않은 onRoutingCompleted를 성공 타이머로 대체하지 않는다. positive 상태가 확인되지 않으면 unknown을 유지한다.
- 제거는 journal이 소유한 M과 현재 M의 이름·ID·원문 좌표 및 D가 일치할 때만 가능하다. FIRST만 제거하고 ALL이나 전체 경로 취소로 대신하지 않는다.
- 앱 재시작은 조회만 한다. 소유 기록을 복원하고 최신 POI 조회를 다시 수행한 뒤 별도 사용자 제거 승인을 받았다. 재시작으로 addWaypoint를 다시 실행하지 않았다.
- 이미 반영된 알려진 요청은 새 세션의 실제 관측으로 명시 확인할 수 있다. 물리 호출을 반복하지 않으며 executorSession과 reporterSession을 구분해 기록한다.

## 4. 이전 unknown의 복구 기록

첫 D 좌표 불일치와 좌표 전용 M의 불완전 조회 이력은 삭제하지 않았다. 순정 UI에서 해당 시험 안내를 종료하고, guest 재시작 후 증가한 bootCount·서로 떨어진 두 새 SDK 조회의 빈 목적지/경유지·SAFE_GUIDING/isRouting=false를 확인한 뒤 복구 확인 버튼을 눌렀다.

원래 outcome=unknown은 유지하고 resolution=recovered_baseline 및 복구 증거를 추가했다. guest-reboot-double-empty-v1은 **이 진단 화면의 목적지 준비 및 자신이 빈 상태에서 만든 시험 D의 add**에 한정한다. 임의의 사용자 경로·unknown remove를 지우는 일반 복구가 아니다.

첫 guest reboot에서 호스트 에뮬레이터가 종료됐고, 재실행 후 시험 앱 등록이 누락돼 동일 APK를 재설치했다. 앱 전용 journal은 재설치 전후 동일 바이트로 남아 있음을 확인했다. 이후에는 `adb shell sync`·`adb emu kill`·Cold boot로 정상 종료/실행했고 패키지·기록이 유지됐다. 앱 데이터 삭제나 wipe-data는 사용하지 않았다.

이 진단 절차가 제품 서버의 RECOVERY_CONFIRM/evidenceId·RESET_ACK를 구현한 것은 아니다. 실제 여정의 운전자 승인·서버 실행권·정리/초기화·미확정 실패 분기는 후속 구현이다.

## 5. 재현 방법

JDK21·SDK35/Build Tools35.0.0으로 vehicle/에서 실행한다.

```sh
./gradlew :app:assembleRealDebug :app:testMockDebugUnitTest :app:lintRealDebug
adb -s emulator-5554 install -r app/build/outputs/apk/real/debug/app-real-debug.apk
adb -s emulator-5554 shell am start --user 10 -n com.waymate.app.real/com.waymate.app.platform.navigation.NaviProbeActivity
```

1. 정차·제한 확인·SDK 연결을 기다린다. 현재 기록/경로가 예상과 다르면 덮어쓰지 않는다.
2. **M POI 위치 확인**을 누르고 위치 검증을 확인한다.
3. 경로가 비어 있을 때 **시험 D 설정**을 누른다. 이미 시험 D만 있으면 다시 설정하지 않는다.
4. **D 유지 · M 추가**를 누르고 applied·D 유지·M ID·관측 증거를 확인한다.
5. 앱을 재실행했다면 M POI를 다시 조회한다. **내 M만 제거**를 누르고 removed·D 유지·경유지 없음·pending 없음·ownsM=false를 확인한다.
6. journal을 읽어 source=real·요청별 attemptId·물리 호출 수를 확인한다.

```sh
adb -s emulator-5554 shell run-as com.waymate.app.real --user 10 cat files/navi-probe.json
```

버튼이 비활성이라면 최신 조회/소유권/제한/기록을 먼저 확인한다. unknown에서 같은 물리 요청을 다시 누르는 방식으로 복구하지 않는다. 이 Activity와 권한은 realDebug에만 포함한다.

## 6. 검증 범위

- 실제 SDK: D 좌표 반영·독립 POI 위치 확인·M 추가·앱 재시작 무재호출·M 제거·D 유지 통과.
- 자동 검증: Node HTTP/계약 52개, Kotlin 내비 정책 9개 통과. 잘못된 좌표·ID·만료/다른 세션 조회·소유권·중복/오래된 관측·복구 조건·느린 조회 간격을 포함한다.
- mockDebug/realDebug APK 빌드·두 Lint 통과(각 오류 0·경고 15). GitHub Vehicle checks도 내비 정책 단위 테스트를 실행하도록 갱신했다.
- 순정 지도 타일 배경 미표시·실차·주행 중 사용은 미검증/미해결이다. 이 결과를 강릉 이야기 ETA·우회 시간 근거로 사용하지 않는다.
- wayMate 제품 화면의 NAV_APPROVE/NAV_DISPATCH_BEGIN/NAV_REPORT·서버 권한·만남·초기화와 연결한 것은 아니다. 제품 navigation capability는 계속 false다. Q28 전체와 W13 전체 완료로 표시하지 않는다.
