# 확장 창 리뷰·앱 글자 확대 검수

2026-11-12. PR #6의 확장 창 리뷰를 실제 Pleos 창에서 재검증했다. **확장 창 2개와 3분할·130% 글자 7개의 기기 UI 테스트가 통과했다.** 순정 내비 배경 지도와 시스템 전체 글자 배율 전환 문제는 미해결이다. 실제 SDK 추가·제거·차량 ACK의 검증 범위는 [17번](17_3분할_검수_및_순정_지도_진단.md)을 따른다.

## 확장 창 리뷰 결과

리뷰 대상은 `CharacterScene`의 `weight(.7f).widthIn(max = 280.dp)`가 확장 결말 화면에서 캐릭터 열을 280dp로 줄이고 약 190dp의 추가 공백을 만드는지였다. Compose의 기본 `weight(fill = true)`가 할당한 최소·최대 너비를 `widthIn`도 따르므로, 실제 측정은 다음과 같다.

| 항목 | 실제 측정 |
|---|---:|
| 앱 창 | 1682×1210dp |
| 캐릭터 열 | 468dp |
| 본문 열 | 1138dp |
| 두 열 사이 | 28dp |
| 좌우 여백 | 각각 24dp |
| 결말 화면 캐릭터 영역 | 468×300dp |

추가 190dp 공백은 재현되지 않았다. 기존 화면과 비교해 외곽 여백이 28→24dp인 차이는 있다. 불필요한 화면 변경 없이 실제 배치 측정과 결말 선택·별도 확인창 회귀 테스트를 추가했다. [확장 결말 원본](evidence/window-review-expanded-ending-2026-11-12.png)과 [측정 JSON](evidence/window-review-validation-2026-11-12.json)을 함께 본다.

## 3분할에서 130% 앱 글자

실제 2560×1440px·160dpi Pleos 화면에서 Driving View / 순정 내비 / wayMate 순서를 사용했다. 앱 창은 `[1718,90]–[2559,1300]`, **841×1210dp**다. 새 테스트 Activity가 가운데에서 열리면 공식 세 손가락 가로 제스처로 오른쪽으로 옮긴 뒤 실제 위치와 크기를 확인한다.

확대는 `mockDebug` 전용 Activity의 `Configuration.fontScale = 1.3`으로 적용한다. **시스템 설정은 1.0을 유지하며 순정 내비를 글자 배율 변경으로 재시작하지 않는다.** 화면 및 Dialog의 실제 `TextLayoutResult` 배율도 각각 1.3인지 확인하고, 글줄의 끝·높이·최대 줄수와 표시·스크롤·클릭을 검사한다.

| 테스트 | 확인한 동작 |
|---|---|
| 홈 | 행동 버튼 4개 도달·표시, 결말 진입 콜백 |
| 공개 질문·말 전달 | 준비된 답변 읽기, 별도 확인 전 전송 0회·확인 후 1회 |
| P04 최종 선택 | 두 선택의 같은 크기, 별도 확인 전 제출 0회·확인 후 1회 |
| 내 캐릭터 결말 | 답변 전체 표시, 일정 왕복 |
| 함께 결말 | 상대 대사·다음 대사, 일정 왕복 |
| 만남→내비 승인 | 추가 확인창, 확인 전 콜백 0회·확인 후 1회 |
| O01 제거 승인 | 제거·돌아가기 확인창, 확인 전 콜백 0회·확인 후 1회 |

선별 원본: [130% 홈](evidence/window-review-font130-home-2026-11-12.png), [최종 선택 확인](evidence/window-review-font130-final-review-2026-11-12.png), [내비 승인 확인](evidence/window-review-font130-navigation-review-2026-11-12.png).

테스트는 실제 화면 Composable에 가상 DTO를 전달한다. Repository·HTTP·내비 SDK·음성 엔진을 생성하지 않고 콜백 횟수만 검사한다. 실제 상대 응답·SDK 변경·GPS·음성 성공 증거로 사용하지 않는다. 실제 앱의 SDK journal 11개 기록은 전후 바이트가 동일했다. 검수 Activity는 `mockDebug`에만 있고 real APK에는 포함되지 않는다.

검수 후 로컬 빌드와 SHA-256이 같은 real APK로 데이터 보존 재설치하고, 시스템 배율 1.0의 [실제 앱·순정 내비 3분할](evidence/window-review-real-home-2026-11-12.png)로 복원했다. 내비의 42dot 안내와 앱의 연결된 홈은 표시되지만 배경 지도는 여전히 없다.

시스템 전체 130% 전환 시 순정 내비 재생성과 경로 유지, 실차 읽기 거리·주행 제한·오디오·프레임/메모리는 별도 검수다. 이 결과를 전체 접근성 검수 완료로 계산하지 않는다.

## 재현과 빌드

JDK 21·SDK 35·Pleos API34 ARM64·160dpi에서 `mock-app/vehicle`을 작업 폴더로 사용한다. 실행 중 실제 앱 데이터나 SDK journal을 지우지 않는다.

```sh
# 실제 Pleos 창을 1682×1210dp로 확장한 뒤
./scripts/verify-window-ui.sh wide

# 순정 내비와 앱이 각각 841×1210dp인 세로 창으로 돌아온 뒤
./scripts/verify-window-ui.sh font
```

스크립트는 현재 Android 사용자를 조회해 mock/test APK를 설치하고, JUnit 성공 개수까지 확인한다. 결과·원본 캡처·APK 해시는 로컬 `mock-app/runtime/window-review-wide` 및 `window-review-font`에 저장한다. `ANDROID_HOME`, `JAVA_HOME`, 필요하면 `ANDROID_SERIAL`을 환경에 맞게 지정한다. 다른 해상도나 창 크기에서는 명시적으로 실패한다.

최종 mock/real/test APK 빌드, Kotlin 39개, 양쪽 Lint 오류 0개가 통과했다. Lint 경고는 각각 26개로, 이전 23개에 테스트 runner 버전 업데이트 안내 3개가 더해졌다. 기존 런타임 라이브러리 버전은 바꾸지 않았다. CI는 기기 UI 테스트 APK의 **컴파일**도 확인하며, Pleos에서 9개를 실행한 결과는 위 수동 기기 실행 증거다. Node 234개는 17번의 선행 검증이며 이번 변경에서 서버 동작은 수정하지 않았다.

## 순정 지도 후속 확인

2026-11-12 [공식 ARM 이미지 목록](https://nexus-playground.pleos.ai/repository/raw-releases/connect-avd/2.x/crp-arm64-sys-img.xml)의 `system-images;android-34;pleos_car_emulator;arm64-v8a` revision은 **2**로 설치된 `package.xml`과 같다. 배포 ZIP의 SHA-1은 `24d28eb2f18eba5e87c861a7eb2bdccebb049419`다. 내부 `source.properties`의 revision 1만 보고 새 업데이트가 있다고 판단하지 않는다.

공식 목록에서 더 새 ARM 수정 이미지를 찾지 못했다. 순정 지도 배경은 여전히 비며, [17번의 재현 조건·제공사 확인 항목](17_3분할_검수_및_순정_지도_진단.md#지도-배경-미해결)을 유지한다. 사용자 키 누락으로 원인을 단정하지 않으며 외부 문의는 발송하지 않았다. PR #6도 Draft를 유지한다.
