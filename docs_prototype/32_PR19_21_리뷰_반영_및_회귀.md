## #21 지연 응답의 대화 대상 고정

전송 시작 때 계정·화면 버전·대화 ID·hash와 원래 대화 객체를 고정한다. 새 대화 생성과 전송은 원래 대상으로 계속 처리하되, 화면이 바뀌었다면 늦은 성공·실패·재조회가 현재 화면·입력·스트림을 갱신하지 않는다. 동일 대화로 돌아왔더라도 이전 화면 버전의 완료 처리는 적용하지 않는다.

재시도·미확인 전송 결과 확인·초안 확정·보관 뒤의 대화 재조회도 같은 범위를 확인한다. SSE는 현재 대화와 같은 ID의 결과만 적용한다. 새 대화 작성 화면에서 다시 새 대화를 선택한 경우도 이전 작업을 무효화한다. 계정 전환 중에 생성된 이전 계정 대화로 새 계정의 전송을 시도하지 않는다.

수정 전 production 핸들러를 실행한 13개 회귀가 입력 덮어쓰기·잘못된 대화 갱신을 검출해 실패했고, 수정 후 통과했다. 추가로 현재 화면의 정상 성공/실패, 재시도·결과 확인과 계정 전환까지 합쳐 UI 회귀 20개를 검증한다. 테스트는 shipped app.js 전체의 핸들러를 node:vm에서 실행하며 DOM/EventSource/API I/O만 대역으로 제어하고 실제 임시 SQLite에 결과를 보존한다.

## #21 미선언 도구와 과거 이력 표시

도구 validator·진행 문구는 Map으로 관리한다. adapter와 runner 양쪽에서 명시된 도구와 입력을 확인한 뒤 실행·이벤트 기록을 수행한다. `constructor`, `toString`, `hasOwnProperty`, `__proto__`, 미선언 이름은 실행되지 않고 정상 도구 이벤트로 남지 않는다.

과거 저장 이력의 진행 문구가 누락·null·숫자이거나 이벤트 배열 자체가 잘못된 경우에는 표시할 수 있는 문자열만 사용한다. 답변과 원문은 그대로 표시하고 문구는 HTML escape한다. 가짜 provider → 실제 adapter/runner/repository, runner 직접 방어, 잘못된 이력의 DB 저장·재시작·실제 렌더러까지 회귀 7개로 검사한다. 실제 OpenAI 호출은 필요하지 않다.

## 브라우저 확인

별도 localhost 테스트 호스트와 임시 DB·합성 계정·응답을 사용했다. 실제 production 웹 파일을 제공하고 A의 POST 202 응답을 B 조회가 일어날 때까지 지연시켰다. 브라우저에서 B에 초안을 입력한 뒤 A에서 전송하고, POST가 끝나기 전에 B를 클릭했다.

B 화면과 작성 초안이 유지됐고, 이후 전송 대상은 B였다. A로 다시 이동해 원래 A 메시지·응답도 저장됐음을 확인했다. 서버에서 실제 전송 순서 A→B와 각 대화의 메시지를 대조했다. 기본 127.0.0.1 서비스와 다른 localhost 쿠키 영역을 사용해 기존 세션·개인 DB를 건드리지 않았다. 임시 브라우저·서버·DB는 검수 후 종료·정리했다.
